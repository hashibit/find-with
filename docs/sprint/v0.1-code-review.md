## Critical Issues

### 1. Auth tokens are not cryptographically secure (`iam.controller.ts`)

**`/auth/exchange`** generates `token = 'ext_' + dto.nonce`. A nonce is a random single-use value—prepending "ext_" to it does not produce a secure session token. This exposes the nonce in the token itself, making the token fully predictable if the nonce is ever observed.

**`/auth/verify`** generates `token = 'ext_' + verified.userId + '_' + Date.now()`. This is guessable to anyone who knows the userId and approximate request time. Neither token is stored or validated anywhere—there is no registry or signature to verify when the extension later uses them. The `UserAuthGuard` presumably validates incoming requests; it's unclear how it validates these unregistered tokens.

**Fix**: Use a CSPRNG token (`crypto.randomBytes(32).toString('hex')`) and store the token hash in Redis with TTL. The guard should look it up on each request.

---

### 2. Token timestamp mismatch between backend and extension — token never expires (`iam.controller.ts`, `extension/auth.ts`)

Backend `authVerify` embeds `Date.now()` (milliseconds, ~1.75 trillion) in the token string. `handleAuthToken` in the extension extracts this value and computes `expiresAt = timestamp + 86400` — adding 86400 seconds to a millisecond-scale timestamp.

The expiry check in `getToken` (`auth.ts:8`) is:
```ts
if (data.expires_at && Date.now() / 1000 > data.expires_at - 300)
```

`Date.now() / 1000` ≈ 1.75 billion (current Unix seconds). `expiresAt - 300` ≈ 1.75 trillion (still ms-scale). The comparison is **always false**: 1.75 billion is never greater than 1.75 trillion.

The consequence is the **opposite** of a premature expiry: the token appears permanently valid from the extension's perspective. Stale tokens are silently retained indefinitely, suppressing any refresh cycle even after the backend stops accepting the token 24 hours later. Users will be silently locked out without any indication.

**Fix**: Use the `expires_at` field returned in the response body (already in Unix seconds) rather than re-deriving expiry from the token string.

---

### 3. Extension token parsing breaks on userIds containing underscores (`extension/auth.ts`)

```ts
const parts = token.split('_');
const userId = parts[1];
```

Token format is `ext_${userId}_${timestamp}`. If `userId` contains `_` (ULID values don't, but Clerk IDs like `user_2abc_xyz` do), `parts[1]` will be wrong and the token will be stored with a corrupted user_id.

## High-Severity Issues

### 5. Every tool execution now does 2 DB writes on the hot path (`agent.service.ts`)

`PendingToolResult` is created and saved before each tool call, then updated after. For a typical 10-iteration agent loop with multiple tool calls per iteration, this adds 20+ synchronous DB round-trips to the agent's critical path. This will increase latency noticeably, especially on tools that return quickly (e.g., `update_radar`).

If the purpose is resumability or observability, consider writing asynchronously via the existing `MEMORY_QUEUE` pattern, or only persisting for tools expected to be long-running (e.g., company research).

Also: the imported `timeout` from rxjs (line 1) is unused.

---

### 6. LLM health check makes a live embedding API call on every `/health` poll (`main.ts`)

`llmProvider.ready()` calls `this.embed('health check')` which issues a real OpenAI API request. Health checks are typically polled every 10-30 seconds by load balancers and orchestrators. This generates constant paid API traffic and adds unnecessary OpenAI dependency to the health endpoint.

Replace with a lightweight check (e.g., verify the API key is configured and the ioredis connection is live).

---

### 7. Sentry sampling at 100% in production (`main.ts`)

```ts
tracesSampleRate: 1.0,
profilesSampleRate: 1.0,
```

100% trace and profile sampling in production will generate extreme Sentry volume and cost under any real load. Standard starting point is 0.01–0.1 (1–10%).

---

### 8. `NonceStore.cleanup()` uses `client.keys('nonce:*')` and deletes live nonces (`nonce.store.ts`)

Two separate bugs:

**Performance**: `KEYS` is an O(N) blocking Redis command that stalls the entire Redis event loop. Under non-trivial key counts this degrades all Redis-dependent operations.

**Correctness**: The comment says "Clean up expired nonces" but `KEYS nonce:*` returns **all** nonce keys including ones still within their TTL that have not expired. The subsequent `client.del(keys)` call deletes them all. Any in-flight auth exchange that has its nonce deleted mid-flight will fail with "Invalid or expired nonce" even though the user did nothing wrong. Since the docstring says "Should be run periodically," this is likely to be called on a schedule in production.

The cleanup function is also redundant in normal operation because Redis TTL handles auto-expiry. The correct fix is to delete the function entirely, or if manual cleanup is truly needed, use `SCAN` and only delete keys whose TTL has already elapsed.

---

### 9. `NonceStore.validate` is not atomic — race condition (`nonce.store.ts`)

```ts
const userId = await client.get(`nonce:${nonce}`);
if (userId) {
  await client.del(`nonce:${nonce}`);
  return userId;
}
```

`GET` and `DEL` are two separate Redis round-trips. Two concurrent requests carrying the same nonce can both complete the `GET` (both see `userId != null`) before either `DEL` runs. Both auth exchanges return a valid userId. The nonce is consumed twice, violating the single-use guarantee.

This is exploitable: an attacker who intercepts a valid nonce during transmission can race the legitimate user and authenticate as them.

**Fix**: Use `GETDEL` (Redis 6.2+) — atomic get-and-delete in a single command. Fallback: a Lua script with atomic `GET` + conditional `DEL`.

---

### 10. `NonceStore.cleanup()` deletes valid in-flight nonces (`nonce.store.ts`)

Separate from the `KEYS` performance issue in finding 8: the correctness bug is that `KEYS nonce:*` returns all nonce keys regardless of remaining TTL, and the subsequent `del(keys)` deletes every one of them. Any legitimate auth flow that has a nonce in Redis when `cleanup()` runs will receive "Invalid or expired nonce" even though the nonce is still valid. The `cleanup()` docstring says "Should be run periodically," making this a production-impacting correctness bug.

**Fix**: Delete the `cleanup()` method. Redis TTL handles expiry automatically. If manual cleanup is ever required for operational reasons, scan only keys past their intended TTL window, not all `nonce:*` keys.

## Medium-Severity Issues

### 11. `OutboxPublisher.countPending` will not filter correctly (`outbox.publisher.ts`)

```ts
return this.outboxRepo.count({
  where: { consumerGroup, dispatchedAt: undefined },
});
```

TypeORM ignores `undefined` in `where` clauses—it does not generate `IS NULL`. This will count all events for the consumer group, dispatched or not. Use `IsNull()` from `typeorm`:

```ts
import { IsNull } from 'typeorm';
where: { consumerGroup, dispatchedAt: IsNull() }
```

---

### 12. Raw SQL `RETURNING` column name mismatch (`outbox.publisher.ts`)

The raw query `RETURNING outbox_events.id, event_type, payload, "consumerGroup"` returns DB column names as-is (snake_case for `event_type`). The TypeScript annotation maps to `eventType` (camelCase). The `logPublishedEvents` call references `e.eventType`—this will be `undefined` at runtime. The actual key will be `event_type`.

---

### 13. `BadRequestException` imported but never used (`tailoring.processor.ts`)

Line 4 adds `BadRequestException` to the import. It is not referenced anywhere in the file.

---

### 14. Redundant second ULID-assignment loop (`tailoring.processor.ts`)

After the `validatedSections` loop already assigns `id = b.id ?? ulid()` to every bullet, there's a second loop:

```ts
for (const section of validatedSections) {
  for (const bullet of section.bullets) {
    if (!bullet.id) bullet.id = ulid();
  }
}
```

The condition `!bullet.id` can never be true at this point. Delete the loop.

---

### 15. `RedisService` uses `any` type throughout (`redis.module.ts`)

```ts
constructor(@Inject(REDIS_CLIENT) private readonly redis: any) {}
get client(): any { return this.redis; }
```

`ioredis` exports a `Redis` type. Use it. The `any` type defeats the compile-time guarantees that make TypeScript worthwhile, and `client` being `any` propagates through all callers.

---

### 16. `encryptedText` column has no encryption implementation (`message.entity.ts`)

The column is defined with a comment "AES-256 for PII protection" but nothing in this diff reads or writes it. The migration will add the column but no code produces or consumes encrypted data. This is a dormant schema change. Either implement the encryption layer (and decide the key management story) or remove the column until it's needed.

---

### 17. `auth/exchange` does not validate nonce format before Redis lookup (`iam.controller.ts`)

Any string is accepted as `nonce`. A malformed or pathologically long string (e.g., 10MB payload) goes directly to Redis as a key. Add a format/length validator on the DTO.

---

### 18. `deepScore` can be negative — no floor clamping (`jobs.processor.ts`)

`text-embedding-3-small` cosine similarity values are in [-1, 1]. If the top-K materials are semantically dissimilar to the JD, `avgSimilarity` is negative, yielding a negative `deepScore` that gets persisted to the DB and included in the advice rationale. A negative match percentage is meaningless and will cause display bugs.

```ts
deepScore = Math.round(avgSimilarity * 100);
// Fix:
deepScore = Math.max(0, Math.round(avgSimilarity * 100));
```

## Low-Severity / Style Issues

### 19. `cosineSimilarity` defined inline in a hot processing path (`jobs.processor.ts`)

The function is re-defined on every `analyzeMatch` call. Move it to a module-level utility or class method.

### 20. `topK` hardcoded to 8 without documentation (`jobs.processor.ts`)

The magic number `8` has no comment explaining the rationale. If the number should scale with JD length or material count, that logic is missing. Add a constant with a comment.

### 21. Duplicate `Inject` import and unused `UseGuards` in `iam.controller.ts`

`Inject` is imported from `@nestjs/common` twice (once in the original import, once in the new lines). Additionally, `UseGuards` is imported but no `@UseGuards()` decorator appears anywhere in the file. Consolidate both into a single clean import.

### 22. `_empty_state_` placeholder text in `Radar.tsx`

```tsx
<div style={{ fontSize: 24, marginBottom: 8 }}>_empty_state_</div>
```

This is a raw placeholder string visible in the UI. Replace with a proper icon or remove.

### 23. All UI routes use inline style objects

`EasyApply.tsx`, `Library.tsx`, `Radar.tsx`, `Tailoring.tsx`, `Onboarding.tsx` are all implemented with inline `style={{...}}` objects. These recreate style objects on every render and make the components hard to maintain. This is acceptable for prototyping but should not merge as-is if these views will be iterated on.
