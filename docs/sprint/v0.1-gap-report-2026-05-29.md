# FindWith v0.1 — Gap Report

> **Date**: 2026-05-29
> **Baseline**: `docs/sprint/v0.1-engineering-sprint-plan.md`, `docs/tech/v0.1-product-design.md`, `docs/tech/v0.1-website-design.md`, `proto/findwith/**`
> **Scope**: Compare plan against current code state in `backend-ts/`, `extension/`, `web/`, `proto/`. Identify gaps that block sprint DoDs and G-1..G-5 gates.
> **Method**: code reading, grep across stacks, migration inspection, U-01..U-12 closure verification.

---

## 0. Executive summary

Five months into the v0.1 plan and the code has drifted hard from the plan in three structural ways:

1. **Stack drift**. Plan specifies Python FastAPI + alembic + uv + arq + pytest with proto-generated Pydantic models. Reality is **NestJS + TypeORM + BullMQ + vitest** in `backend-ts/`, and **`proto/findwith/**` is dead source-of-truth** — `buf.gen.yaml` points at `backend/app/generated/proto` (a Python path that doesn't exist) and `extension/src/shared/proto/` (also doesn't exist). The backend wires DTOs from `nestjs-zod`, not from generated proto types. This means every plan invariant that depends on "buf breaking" CI, "alembic check --autogenerate", pgcrypto/DEK/KEK, and Pydantic schema enforcement is **structurally unenforceable** as written. Either retire the proto/ tree or wire it back in.

2. **Front-of-house is paper**. All six Side Panel routes (`Onboarding.tsx`, `JobAnalysis.tsx`, `Tailoring.tsx`, `Radar.tsx`, `Library.tsx`, `EasyApply.tsx`) are 10–12 LOC stubs returning "Generate a tailored resume…" placeholder text. Only one shared component exists (`ConversationView.tsx`). P1-S6 / P3-S9 / P3-S10 / P4-S11 UI deliverables are 0% built. G-1 (look-through Profile editor) and G-2 (bullet PENDING/CONFIRMED state UI) cannot be demonstrated.

3. **Auth flow is functionally broken end-to-end** (but not exploitable). The U-03 "OAuth-style code flow" is half-wired in three places that don't talk to each other:
   - `web/src/app/auth/extension-callback/page.tsx:33` sends `{ type: 'AUTH_TOKEN', token: <rawClerkJwt> }` to the extension via `chrome.runtime.sendMessage(EXT_ID, ...)`.
   - `extension/src/background/index.ts:22` only handles `AUTH_NONCE` and `ENTITLEMENTS_INVALIDATE` — `AUTH_TOKEN` falls off the listener and is silently dropped. No token is ever persisted in `chrome.storage`.
   - `extension/src/background/auth.ts:21` calls `POST /v1/iam/auth/exchange`, but there is **no `auth/exchange` endpoint in the backend** (`grep -r 'exchange\|nonce\|auth_code' backend-ts/src` = 0 hits).

   Net: no user can authenticate the extension via the website. The website login → extension JWT path is unreachable. This blocks P0-S2 DoD and P5-S13 G-4. **Note on severity**: the original U-03 wire-vulnerability ("raw JWT via sendMessage") does *not* actually materialize — there is no consumer for the `AUTH_TOKEN` message, and `chrome.runtime.sendMessage` with explicit `EXT_ID` only reaches that one extension (Chrome Web Store enforces ID uniqueness). The defect is a functional blocker, not a security incident.

The rest of this document inventories what is and isn't built, sprint by sprint and U-item by U-item.

## 3. New code since last review — memory subsystem

Three new commits land a 4-layer memory system (`820a41b`, `9501869`):

- `backend-ts/src/contexts/memory/{memory.module,memory.processor,memory.constants}.ts` (235 LOC).
- New entity `UserGoalMemory` + migration `1780090000000-AddMemoryTables.ts` (47 LOC) adding `conv_rolling_summary` and `user_goal_memory`.
- `agent.service.ts` enqueues `compress` and `extract` jobs at end of each agent turn.

**Observations**:

- **Goal extraction prompt** (`memory.processor.ts:16`) is inline; not in PromptRegistry. Same problem as every other prompt in the codebase.
- **`extractPreferences` merge strategy is union-only** (`mergeStringArray`). A user who says "I don't want to work at startups anymore" cannot remove `startup` from `targetIndustries` — the merger only adds. The prompt asks for `dealBreakers` but the implementation never lets a user *retract* a previously declared preference. Decide whether this is by design (history-respecting) or a bug; either way, document it.
- **`compressConversation` BullMQ enqueue is per-turn**, not gated by message count / age. On a noisy onboarding session this re-compresses on every turn — wasted LLM spend. Plan §14.7 specified daily APScheduler.
- **`conv_messages.archived` flag** added (migration `1780076958628`) but `context-builder.service.ts` should filter on it — verify.
- The whole memory pipeline runs **after** SSE `done` is emitted (good for latency) but **without retry visibility in Side Panel** — if extract fails the user never knows their preferences weren't captured. Add telemetry `memory.extract.failed` at minimum.

## 6. Top-10 prioritized gap list (highest leverage first)

1. **Fix auth flow end-to-end (U-03)**. Implement `POST /v1/iam/auth/exchange` in backend, switch `web/src/app/auth/extension-callback/page.tsx` to nonce flow, align `extension/src/background/index.ts` message type. Without this, every other backend feature is unreachable from the extension.
2. **Tighten match scoring algorithm**. `jobs.processor.ts:147–179` uses pure substring matching for both surface and deep scores — `jdEmbedding` and `profile_materials.embedding` are written but never consumed in scoring. Either wire embeddings into the "deep" layer (cosine vs. each user material like `context-builder.service.ts` already does for Layer 3 selection) or drop the Spearman ≥0.7 invariant from G-3. Note: pgvector still not required at v0.1 scale — in-process cosine is sufficient.
3. **Bullet fail-fast invariant**. In `tailoring.processor.ts`, after LLM JSON parse, reject the entire output (or downgrade to PENDING) for any bullet without a valid `sourceId` pointing at a CONFIRMED/USER_EDITED material owned by the user. Add a DB CHECK or service-level invariant test.
4. **Build the Side Panel**. Onboarding wizard, Tailoring diff view with bullet color states, Radar list, Library tagged-by-domain view, EasyApply preview/approve. Without these, G-1/G-2/G-3 are unreachable regardless of backend state.
5. **Outbox publisher worker** (BullMQ-equivalent, since arq isn't used): query `outbox_events WHERE consumerGroup=$1 AND dispatchedAt IS NULL FOR UPDATE SKIP LOCKED`, dispatch, mark dispatched. Without this, no domain events propagate (entitlements changes, offer-accepted farewell, etc.).
