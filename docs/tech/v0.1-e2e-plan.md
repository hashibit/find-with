## 1. Scope

E2E tests cover exactly six user journeys that form the product's critical path. Anything not on this list is unit/integration-tested instead.

| ID   | Journey                      | Entry point                     |
|------|------------------------------|---------------------------------|
| J-01 | Onboarding (resume → profile)| Extension side panel first open |
| J-02 | Job analysis ("Ask Quinn")   | LinkedIn fixture page           |
| J-03 | Resume tailoring + export    | Radar → "Start tailoring"       |
| J-04 | Radar status progression     | Multiple job interactions       |
| J-05 | Email capture + classification| Gmail fixture page               |
| J-06 | Offer farewell               | User sends "I accepted an offer"|

**Explicitly out of scope at this layer:**

- Stripe checkout UI (StubPaymentAdapter returns a stub URL; billing flows are integration-tested separately)
- Clerk OAuth login screen (DevAuthAdapter bypasses it entirely)
- Real LinkedIn/Indeed scraping (served from local nginx fixture)
- True Service Worker kill/restart cycle (needs real Chrome in L5 OrbStack env)
- LLM response quality judgment (handled in L6 LLM-driven manual layer)
- Subscription auto-pause on offer acceptance: PRD §9.4 requires this but it is **not implemented in v0.1**. When the feature lands, add `BillingSubscription."state" = 'PAUSED'` assertion to J-06.

## 2. Auth and Subscription Bypass

### 2.1 Auth (Clerk replacement)

The backend's `IamModule` already selects the adapter at startup:

```typescript
// Non-production → DevAuthAdapter
// verify(token: string) returns { userId: token }
```

When `NODE_ENV=test`, **Bearer token = userId string directly**. No JWT signature, no JWKS fetch.

For e2e, the extension background script receives a pre-set token from a test fixture injected at page load. The token value is the seed user ID (e.g., `e2e-user-1`). The backend accepts it as a valid identity.

**Extension side**: inject a test override in `chrome.storage.local` before each test:

```javascript
await page.evaluate(() => {
  chrome.storage.local.set({
    auth_token: 'e2e-user-1',
    auth_expires_at: Math.floor(Date.now() / 1000) + 3600,
    user_id: 'e2e-user-1',
  });
});
```

This bypasses the nonce → token exchange flow entirely for e2e purposes.

### 2.2 Subscription / Quota (Stripe replacement)

When `NODE_ENV !== 'production'`, `StubPaymentAdapter` is used and returns stub URLs for checkout/portal. Quota state is read from the `BillingSubscription` entity in Postgres, not from Stripe.

Seed a PRO subscription row directly in the test database at fixture setup. Column names are **quoted camelCase** (no naming strategy in the project — identifiers match TypeORM entity properties verbatim):

```sql
INSERT INTO billing_subscriptions ("userId", "tier", "state", "periodEnd")
VALUES ('e2e-user-1', 'PRO', 'ACTIVE', now() + interval '30 days');
```

The quota check then resolves against real DB state, exercising the full quota code path without touching Stripe.

## 3. LLM Mock

### 3.1 Strategy

Point the backend's OpenAI client at a local mock server via env:

```
OPENAI_BASE_URL=http://localhost:11435/v1
OPENAI_API_KEY=e2e-test-key
```

The mock server (`e2e/llm-mock/server.ts`) is a minimal Express app that matches incoming requests by endpoint + a normalized fingerprint of the `messages` array, then returns a recorded golden fixture.

**Hash normalization** (applied before SHA-256 of the serialized `messages` array):
1. Replace all 26-character uppercase ULID tokens (`[0-9A-Z]{26}`) with `<ID>`
2. Replace all ISO-8601 datetime strings (`\d{4}-\d{2}-\d{2}T[\d:.Z+-]+`) with `<TS>`
3. Replace all 13-digit numeric epoch-millisecond values (`\d{13}`) with `<EPOCH>`

Without these normalizations, ULIDs and timestamps embedded in prompts would produce different hashes on every run.

### 3.2 Recording workflow

1. Run with `LLM_RECORD=true` against real OpenAI once per scenario.
2. Fixtures written to `e2e/fixtures/llm/`.
3. Subsequent runs replay from fixtures. Hash mismatch → test fail with diff output.

### 3.3 Fixture structure

```
e2e/fixtures/llm/
  onboarding-resume-parse.json       # J-01: resume → structured profile
  job-analysis-jd-parse.json         # J-02: JD → structured requirements
  job-analysis-company-research.json # J-02: company lookup summary
  job-analysis-match-score.json      # J-02: three-layer match
  tailoring-initial-draft.json       # J-03: initial tailored bullets
  tailoring-gap-mining.json          # J-03: gap conversation turn
  tailoring-bullet-edit.json         # J-03: single bullet rewrite
  followup-email-classify.json       # J-05: classify email as interview invite
  farewell-summary.json              # J-06: farewell + journey recap
```

Each fixture file:

```json
{
  "endpoint": "/v1/chat/completions",
  "requestHash": "sha256 of normalized messages array",
  "response": { /* OpenAI-compatible response body */ }
}
```

### 3.4 Embedding mock

For pgvector similarity queries, the mock server also intercepts `/v1/embeddings` and returns a fixed 1536-dim vector keyed by input text hash. This keeps semantic search deterministic without a real model.

## 4. External Service Mocks

### 4.1 LinkedIn / Indeed DOM fixtures

A local nginx container serves static HTML pages at `http://localhost:8081`. The extension's content script is configured to treat this origin as a whitelisted job board during tests via a **build-time manifest patch** (see §5.3).

Fixture pages:

```

  gmail-rejection.html             # J-05: rejection email
```

Fixtures are recorded once with real browser + real pages (sensitive data scrubbed), then committed. Updated on meaningful LinkedIn/Gmail DOM structure changes.

Already covered by `docker-compose.test.yml`. Resume PDF uploads, profile exports, and tailoring plain-text exports use MinIO at `http://localhost:9000`. Bucket `findwith-test` is auto-created on container startup.

### 4.3 SMTP (recommendation emails)

Mailpit container at `localhost:1025` (SMTP) / `localhost:8025` (UI). Post-apply follow-up email assertions check Mailpit's REST API.

### 5.3 Extension e2e build

The production manifest (`extension/dist/manifest.json`) must never be modified. The e2e build produces a **separate** `extension/dist-e2e/` with an overridden manifest:

**`e2e/manifest.e2e.json`** (patch applied at build time):
```json
{
  "key": "<base64-encoded-public-key-from-e2e/extension-key.pem>",
  "host_permissions": [
    "https://api.findwith.com/*",
    "https://*.linkedin.com/*",
    "https://mail.google.com/*",
    "http://localhost:14668/*",
    "http://localhost:8081/*"
  ],
  "content_scripts": [
    {
      "matches": ["https://www.linkedin.com/jobs/*", "http://localhost:8081/linkedin-*.html"],
      "js": ["cs-linkedin-job.js"]
    },
    {
      "matches": [
        "https://www.linkedin.com/jobs/*/easy-apply/*",
        "https://www.linkedin.com/jobs/search/*"
      ],
      "js": ["cs-linkedin-apply.js"]
    },
    {
      "matches": ["https://mail.google.com/*", "http://localhost:8081/gmail-*.html"],
      "js": ["cs-gmail.js"]
    }
  ],
  "externally_connectable": {
    "matches": ["https://findwith.com/*", "http://localhost:14666/*", "http://localhost:14668/*"]
  }
}
```

**Key stability**: generate once with `openssl genrsa 2048 > e2e/extension-key.pem`. Derive the extension ID from the public key and set `CORS_ORIGINS` in `.env.e2e`. Commit the PEM (it's test-only, no production secret).

**`global-setup.ts`**:
1. Start Docker Compose services
2. Run TypeORM migrations: `dotenv -e .env.e2e -- pnpm migration:run`
3. Seed fixture data (users, subscriptions, materials)
4. Start backend server on port 14668
5. Build extension e2e variant: merge manifest.e2e.json patch into production manifest → output to `extension/dist-e2e/`

**`global-teardown.ts`**:
1. Stop backend server
2. `docker compose -f docker-compose.e2e.yml down -v`

### 8.2 DOM polling helpers

Extension SSE events travel through the Chrome runtime message bus (`port.postMessage`), not `window.dispatchEvent`. Tests must assert on **rendered DOM state**, not on transport events.

```typescript
// e2e/helpers/sidepanel.ts
async function waitForElement(page: Page, selector: string, timeout = 30_000): Promise<void> {
  await page.locator(selector).waitFor({ state: 'visible', timeout });
}

// Examples:
await waitForElement(page, '[data-testid="agent-message"]:last-child');
await waitForElement(page, '[data-testid="job-analysis-complete"]');
await waitForElement(page, '[data-testid="farewell-message"]');
```

> **Selector audit required**: selectors above are placeholders. Before writing tests, audit `extension/src/sidepanel/components/**` for existing `data-testid` attributes. Add missing ones in the same PR as the test that depends on them. Do not add `data-testid` attributes to production components just to satisfy tests without checking existing conventions first.

Backend state assertions use direct DB queries (pg client in test process) or REST calls — not page context.

### 8.3 Extension ↔ backend communication

The extension background service worker forwards API calls. Playwright communicates with the side panel page directly via page context, not the background worker. Assertions on backend state go via direct DB queries or REST calls from the test process.

## 9. CI Integration

E2E tests run in a separate GitHub Actions job triggered on main push and nightly — **not** on every PR (runtime ~15 min).

```yaml
# .github/workflows/e2e.yml
name: E2E

on:
  push:
    branches: [main]
  schedule:
    - cron: '0 2 * * *'   # nightly
  workflow_dispatch:
    inputs:
      record_llm:
        description: 'Record LLM fixtures (true/false)'
        default: 'false'

jobs:
  e2e:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: 'pnpm' }
      - uses: coactions/setup-xvfb@v1   # required — Side Panel API needs headful Chrome
      - run: pnpm install
      - run: pnpm build:extension:e2e   # produces extension/dist-e2e/ with manifest patch
      - run: pnpm build:backend
      - name: Start services
        run: docker compose -f docker-compose.e2e.yml up -d
      - name: Wait for services
        run: ./e2e/scripts/wait-for-services.sh
      - name: Run migrations
        run: cd backend-ts && dotenv -e .env.e2e -- pnpm migration:run
      - name: Run e2e
        env:
          LLM_RECORD: ${{ github.event.inputs.record_llm || 'false' }}
          DISPLAY: ':99'
        run: pnpm e2e
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: playwright-report
          path: e2e/playwright-report/
```
