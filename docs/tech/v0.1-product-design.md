### 1.2 关键架构决策（trade-off 已明示）

| 决策 | 选择 | 拒绝项 / 原因 |
|---|---|---|
| 部署形态 | **单 FastAPI monolith + 独立 worker 进程**（产品 API 端） | 不上 K8s/微服务；单人团队，模块通过包边界隔离即可 |
| 产品 / 官网拆分 | **两个独立服务，共享同一 Postgres + Clerk** | 产品 API（api.findwith.com）服务扩展；官网（findwith.com）独立 Next.js + Vercel；订阅状态写入共享 DB，产品端只读。详见 §15 协议 |
| 对外协议 | **REST + JSON over HTTPS（Connect/grpc-gateway 风格）**；定义用 protobuf，运行时 schema 用 buf+protoc-gen-pydantic 生成 | 不上 gRPC：Chrome MV3 service worker 不支持 HTTP/2 trailers；JSON 调试友好 |
| 流式 | LLM 输出走 **SSE**；轻状态变更用轮询 + ETag | 不上 WebSocket：MV3 的 service worker 30s 自动休眠，SSE 比 WS 简单可靠 |
| LLM 抽象 | 自建 **LLM Gateway**（Strategy 模式封装 OpenAI/Anthropic）；工具用 OpenAI tool-calling 协议作内部 IR | 不直接捆绑 SDK 入服务层（违反 DIP） |
| 队列 | **arq** (Redis-based) + **APScheduler**（cron） | 不上 Celery：依赖太重；arq 对 asyncio 原生支持 |
| 抓取 | LinkedIn/Gmail 全部走**用户浏览器内的 content script** | 不在服务端爬 LinkedIn/Gmail：被反爬 + 隐私违规 + 跟产品调性不符 |
| schema | protobuf 是 **唯一来源（SSoT）**，Pydantic、TypeScript、SQLAlchemy 列名都派生 | 不让三端各写一份 model |
| 多租户 | 单 DB 多 schema（`public.users.id` 作 row-level 隔离），后期再切 RLS | v0.1 不上 PostgreSQL RLS——开发慢，单体足够 |

## 二、领域划分（高内聚 / 低耦合）

按 DDD bounded context 切，每个 context 在仓库里是一个 Python 包（`app/contexts/<name>/`），互相只通过显式接口（端口）和 **DomainEvent** 通信。

**产品端共 11 个 context**（原 13 个减去：`billing` 拆到官网；`notification + telemetry → infra`）。其余领域 context 各自独立——`profile/jobs/tailoring/apply/followup` 各只做一件事，不合并到 `delivery` 这种胶水包，理由是新功能（如 Workday 多页填表）会在原边界内自然加 adapter，合并后还要再拆。

`quota` 留在产品端而非合并到 `iam`：quota 真正的扣减发生在用户用扩展导出 PDF 时，逻辑属于产品端；它只读 `subscription.tier` 一字段（来自官网写入的 `billing_subscriptions` 表）作为限额上限。这是清晰的"读侧依赖"，与 DIP 一致。

| Context | 职责 | 不做 |
|---|---|---|
| `iam` | Clerk JWT 校验、本地 user 表懒同步、读取订阅 entitlements、暴露 `/v1/me/entitlements` | 不存密码、不调 Stripe（写入由官网做） |
| `quota` | 免费档"3 个完整定制岗位"计数、`consume_on_export` 扣减、升级提示触发 | 不知道 Stripe（只读 `subscription.tier`） |
| `profile` | 简历解析、档案 CRUD、素材库、闪光点提炼、多版本主简历 | 不知道 JD |
| `jobs` | JD 抓取入参规范化、JD 解析、公司研究、三层匹配、雷达状态 | 不写简历 |
| `conversation` | 消息持久化、上下文窗口管理（rolling summary + RAG）、陪伴密度 | 不调 LLM |
| `agent` | Quinn 编排：system prompt 组装、tool registry、流式产出、密度临时切换 | 不直接读 DB |
| `tailoring` | 初版生成、bullet 溯源、缺口挖掘、待确认机制、PDF/纯文本导出、快照 | 不投递 |
| `apply` | Easy Apply 填表计划生成、提交回执登记 | 不点 Submit |
| `followup` | 邮件 DOM 解析、邮件分类、关键信息提取、回信草拟、状态同步 | 不接 Gmail API |
| `recommendation` | 每日推荐生成、邮件渲染、反馈学习 | 不发邮件（委托 `infra`） |
| `infra` | 共享工具层：Resend 邮件发送 + 事件埋点入库 + Sentry breadcrumb | 不含领域逻辑；不决定何时发邮件、不做 BI 报表 |

**模块依赖方向**（DAG，禁止反向 import）：

```
agent → conversation → llm_gateway
agent → (profile, jobs, tailoring, apply, followup) via Tool Port
tailoring → profile, jobs
apply → tailoring, jobs
followup → jobs, conversation
recommendation → profile, jobs, infra
quota → iam (read-only: subscription.tier 来自官网写入的同 DB 表)
all → iam (auth), infra (write-only ports: telemetry events + email)
```

## 四、关键业务流（含数据流）

### 4.1 上传简历 → 深度档案 onboarding（profile 域）

```
[Side Panel] ─UploadResume(bytes)──▶ POST /v1/profile/resumes
                                    │ 1. 鉴权 (Clerk JWT)
                                    │ 2. 配额: free 也允许
                                    │ 3. 写 ResumeSource (status=PENDING)
                                    │ 4. enqueue arq job: parse_resume(resume_id)
                                    ▼
                              {resume_id}
[Side Panel] 轮询 GetParseStatus / 或订阅 SSE /v1/conversations/{id}/events
[Worker]  parse_resume:
   pdf/docx → text → LLM(prompt=ParseResumeV1) → Profile JSON
   写入 profile.* 表; 更新 ResumeSource.status=PARSED
   发布 DomainEvent: ProfileParsed
[Agent]  监听 ProfileParsed → 创建 Conversation(kind=ONBOARDING)
                              → SSE 推 "我看完了，先确认一下..."
[User] 回复 → /v1/conversations/{id}/messages (stream=true)
[Agent] orchestrator:
   ├ 装配 system prompt v1 (F-901, 含 density)
   ├ 注入 上下文 (rolling_summary + last 8 messages + Profile snapshot)
   ├ 调 LLM with tools=[mine_shining_point]
   └ tool_call(mine_shining_point) → MaterialItem(status=PROPOSED)
                                  → 流回 SSE: state.material.proposed
[Side Panel] 闪光点卡片浮现 → 用户确认 → /materials/{id}/confirm
```

**关键不变量**

- 任何 `MaterialItem` 必有 `Provenance`（`ConversationSource` 或 `ResumeSource`）；DB 约束 `CHECK (provenance_kind IS NOT NULL)`。
- `mine_shining_point` 工具的输出走 **`outbox` 表**（事务性出箱），由独立 publisher 推送 SSE，避免"DB 写成功但 SSE 丢"。

### 4.2 LinkedIn JD → 三层匹配 → "要不要投"

```

   注入 "问问 Quinn" → 点击 →

[service worker] POST /v1/jobs/captures (idempotency-key = sha256(source_url+capturedAt-day))
[backend jobs ctx]
   1. 写 JobCapture
   2. 同步: 创建 RadarItem (status=BROWSED)
   3. enqueue: parse_jd(capture_id), build_company_brief(company)
```

### 4.3 教练式简历定制（产品的灵魂）

```
触发: 用户在分析页选 "想投" → POST /v1/tailoring  body={radar_item_id, base_resume_id}
QuotaService.check(user, 'tailoring')      # ⚠️ 只读门禁：不够则 402，不扣减
                                            # 真正扣减发生在 export 时（见下）
TailoringService.create:
   1. 加载 Profile + Materials(top-K by JD via pgvector) + ParsedJd
   2. LLM(GenerateTailoredResumeV1) → TailoredResume
      - 每条 bullet 必须返回 source_material_ids；
        若空 → state=PENDING（待确认）；不允许"凭空创作"
   3. compute match_after → 写回
   4. 创建 Conversation(kind=GAP_MINING, anchor=tailored_id)
        for gap in gaps where kind=NEEDS_MINING: 推送提问 (F-404)

[用户回答] → 同 4.1 流，触发 mine_shining_point tool → MaterialItem(status=PROPOSED)
[Agent] ⚠️ 不直接 re_apply：该 tool 的 `requires` 前置条件是 material.status ∈ {CONFIRMED, USER_EDITED}
        而是 SSE 推送 "闪光点卡片" 给用户（state=material.proposed, payload=card_data）
[Side Panel] 渲染卡片：
   ┌──────────────────────────────────────────┐
   │ 我从你刚才的话里提取到一条闪光点：         │
   │ "在团队效率提升 25% 中起到关键作用..."     │
   │ [✏ 改一改] [✓ 确认 + 应用到简历]          │
   └──────────────────────────────────────────┘
[用户点 ✓] → POST /materials/{id}:confirm + 同步 PATCH tailored_resume:re_apply
   后端事务：
     1. material.status = CONFIRM_CONFIRMED
     2. ToolGateway.invoke('re_apply_material_to_tailoring', {material_id, tailored_id})
        - 该 tool 启动时再次校验 requires；不满足直接拒绝（防绕过）
     3. 更新 bullet（找到 source_material_ids 含 material_id 的 PENDING bullet）→ state=CONFIRMED
     4. recompute_match → 写 match_after
     5. SSE 推 state: "match: 83 → 89"
[用户点 ✏ 改一改] → 进入对话 inline 编辑 → PATCH material.shining_text
                    → status 转 CONFIRM_CONFIRMED（用户改过即视为确认）
                    → 同上路径触发 re_apply

[用户编辑 bullet] PATCH /v1/tailoring/{id}/bullets/{bid}
            body={kind:'natural_request', text:'缩短一点'}
            → LLM(EditBulletV1) → 新 bullet（state=USER_EDITED, 原溯源保留）

[导出] POST /v1/tailoring/{id}/exports?fmt=pdf
   预检：扫描所有 bullet.state；若任一为 PENDING → 422，前端高亮黄色待确认
   渲染（Jinja + WeasyPrint） → S3 → ResumeSnapshot
   ⚠️ Quota 在此处真正消费（见 P-07 规约）：
     QuotaService.consume_on_export(user_id, tailored_resume_id):
       BEGIN; SELECT * FROM quota_usage_counters WHERE user_id=? FOR UPDATE;
       IF NOT EXISTS (SELECT 1 FROM quota_consume_log WHERE tailored_resume_id=?) THEN
         UPDATE quota_usage_counters SET tailoring_completed = tailoring_completed + 1;
         INSERT INTO quota_consume_log(tailored_resume_id) VALUES (?); -- UNIQUE 防重扣
       END IF; COMMIT;
   → DomainEvent: TailoringExported (driver: 升级提示判定)
```

**信任机制实现细节**

- `bullet.state=PENDING` 在 PDF 渲染时 **拒绝输出**，强制用户先确认/补量化。
- 渲染白名单：`state ∈ {TRACED, USER_EDITED, CONFIRMED}`。
- "待确认"在 UI 上是黄色 + inline confirm prompt（原型里有此态位）。
- `Provenance` 在 PATCH 时只能"在原 trace 上叠加 user_edited_at"，不能丢；DB 用 trigger 防误删。

**Click 链接签名（防伪造、防爬虫枚举）**

邮件里的 click URL 是公网可猜的（user_id + reco_id 都是 ULID 但仍被邮件代理 / 爬虫预取），不签名会被假点击污染 funnel。也不能依赖 `Referer`：邮件客户端（Gmail/Outlook web）多数策略下不发 referer，签名机制必须独立于请求头。

签名方案：

```
sig = base64url(HMAC-SHA256(SERVER_SECRET, f'{user_id}|{reco_id}|{reco_sent_at_day}'))
       └─ 截断到 16 字节，URL 安全
reco_sent_at_day = YYYYMMDD（UTC）of 邮件发送日
```

服务端 `/v1/r/{user_id}/{reco_id}/click`：

1. 重算 sig，与 query 比对（`hmac.compare_digest`，防时序攻击）；不一致 → **直接 404**（不 302、不打 telemetry，避免给爬虫信号）
2. 读 `Recommendation.sent_at`，若 `now - sent_at > 30d` → 404（防签名永久有效，30d 后链接失效）
3. 通过 → 写 `recommendation_clicks(user_id, reco_id, clicked_at, ip_hash, ua_hash)`
4. UNIQUE `(user_id, reco_id)` 部分索引：邮件代理预取 / 用户多次点击只算一次有效 click，重复直接 ack 跳转
5. 302 → canonical URL

`SERVER_SECRET` 走 Doppler / KEK 同源，轮换时旧 secret 保留 30 天双签验证（覆盖未点击邮件的链接寿命）。

**成本归属**：SerpAPI 月费 $50（5000 次搜索，约支撑 100 个 Pro Plus 用户 × 30 天 = 3000 次）。该成本计入 Pro Plus 档独享功能，不在 Pro 档暴露。Brave Search API 作 fallback：每千次 $3，更适合应急。

**MV3 service worker 的 SSE 实现**

⚠️ **`EventSource` 在 service worker 全局不可用**（HTML Living Standard 把 EventSource 限定在 Window/Worker 全局，但 ServiceWorkerGlobalScope 不在白名单；Chrome 实测 `typeof EventSource === 'undefined'`）。改用 `fetch + ReadableStream` 手写 parser：

```ts
// background/sse.ts
async function openSseStream(url: string, lastEventId?: string) {
  const ctrl = new AbortController();
  const headers: HeadersInit = {
    Accept: 'text/event-stream',
    Authorization: `Bearer ${await getToken()}`,
  };
  if (lastEventId) headers['Last-Event-ID'] = lastEventId;

  const resp = await fetch(url, { headers, signal: ctrl.signal });
  if (!resp.ok || !resp.body) throw new Error(`SSE open failed: ${resp.status}`);

  const reader = resp.body.pipeThrough(new TextDecoderStream()).getReader();
  let buf = '';
  while (true) {
    const { value, done } = await reader.read();
    if (done) break;
    buf += value;
    let idx;
    while ((idx = buf.indexOf('\n\n')) >= 0) {
      const block = buf.slice(0, idx);
      buf = buf.slice(idx + 2);
      const ev = parseSseBlock(block);   // → { id?, event?, data }
      if (ev.id) await chrome.storage.session.set({ lastEventId: ev.id });
      forwardToSidePanel(ev);
    }
  }
}
// parseSseBlock: 按 spec 处理 'id:'/'event:'/'data:'/comment 行
```

**断线/SW 重启续传**

- 持久化：`lastEventId` 存 `chrome.storage.session`（SW 唤醒后可读，浏览器关闭即清，符合一次会话语义）
- 重连：SW 被 30s 杀掉再次唤醒（用户切 tab、收消息）→ `chrome.alarms` 回调或 connect 触发 → 重新 `openSseStream(url, lastEventId)`
- 后端：消息按 ULID 单调；server 在 `Last-Event-ID` 之后回放未确认消息（`outbox_events` 表保留 24h）

**降级 fallback（>30s 仍连不上）**

- 进入轮询：`GET /v1/conversations/{id}/messages?since=<lastEventId>&wait=10`（long-poll，10s 内有新消息即返回）
- UI 标记 "连接较慢"；连续 3 次轮询成功后尝试切回 SSE
- telemetry: `sse.fallback_to_polling` 计数

**单条 assistant message 跨进程续传**

适用场景：流式响应进行到一半，Chrome 整个 quit / 用户重启 → SW 销毁 → SSE 上下文丢失。重开后用户进 Side Panel 看到 conversation 列表里那条 assistant message 处于"未完成"（finish_reason=null）。

```
POST /v1/conversations/{id}/messages/{msg_id}:resume
   Body: { last_event_id?: string }   # 可选，无则从 message 开头回放
   Response: SSE stream
[backend]
   1. SELECT * FROM conv_messages WHERE id=msg_id AND conversation_id=id
      若 finish_reason 非空 → 直接 JSON 返回完整 message（200，不开 SSE）
      若 finish_reason 为空 → 进入 SSE
   2. 从 outbox_events 找 conversation_id=id 且 message_id=msg_id 的 events
      根据 last_event_id 截取后续，逐条 SSE replay
   3. 检查 worker 状态：若 LLM 仍在跑（lock 未释放）→ 续上原 stream
                       若 LLM 已挂（worker 崩了）→ resume 时重新调度一次：
                         读已生成的 partial token → 作为 LLM continuation prompt → 续写
                         记 conv_messages.meta.resumed_count（含次数防无限循环，上限 3）
   4. 终态时关流
```

`outbox_events` 至少保留 24h（与 telemetry 月分区不同），超出则视为不可恢复，UI 提示"中断未恢复，重新发送一次"。

⚠️ resume 是幂等的：多次调用同一个 msg_id 收到的 partial 流相同（按 last_event_id 截取一致）。

**异步工具调用的 UI 状态机**

部分 tool 是异步的（如 `parse_resume`、`build_radar`、`tailor_resume`），从触发到 finish 可能 30s–3min。期间用户看到的 UI 必须明确，避免重复点击导致重复 LLM 计费 / 重复落库。

```
状态机：IDLE → SUBMITTING → IN_FLIGHT → DONE / FAILED
触发按钮（"开始定制"）：
  IDLE      →  enabled，灰色文案
  SUBMITTING→  disabled，spinner，"提交中..."
  IN_FLIGHT →  disabled，进度条 + cancel 按钮，"AI 正在分析（已 12s）"
  DONE      →  re-enabled，但按钮文案变 "重新生成"
  FAILED    →  re-enabled + 错误提示 + "重试"
```

**幂等约束**（防重复点击 / 防 SW 重启重发）：

- 客户端 SUBMITTING 时生成 `idempotency_key = ULID()`，POST 到 `/v1/tailoring:create` header `Idempotency-Key`。
- 服务端 `idempotency_keys(key, user_id, response_body, created_at)` TTL 24h；命中 in-flight → 返回原 conversation_id + message_id，UI 直接 attach 到原 SSE 流；命中 done → 返回原 response。
- SW 重启后，Side Panel mount 时检查 `chrome.storage.local.in_flight_tools[]`，自动 reattach 未完成的 tool 流。
- 取消按钮：发 `POST /v1/conversations/{id}/messages/{msg_id}:cancel`，server 通过 cooperative flag 让 worker 在下一个 LLM step 边界中断（不杀已发出的 LLM 请求，但不计后续步骤）。

### 8.3 登录态同步（F-802）+ Token 刷新

**初次登录（nonce 握手，不传 raw token）**

把网页内的 raw Clerk JWT 直接 `sendMessage` 到扩展是反模式：网页 DOM 一旦被 XSS 或浏览器扩展（其它扩展）窥探，token 立刻泄漏；token 寿命较长（Clerk session 默认 1h），危害放大。改为 **nonce 握手**（参考 GitHub CLI device-flow 的扩展版）：

```
[网站 success page]
  1. POST /v1/auth/ext-link-nonce          (Clerk session cookie 带上)
     → { nonce: <ULID>, expires_at: now+60s }
  2. chrome.runtime.sendMessage(EXT_ID, { type:'AUTH_NONCE', nonce })
     ↑ payload 里只有一次性 nonce，泄漏无意义

[SW 收到 AUTH_NONCE]
  3. POST /v1/auth/ext-link-confirm  body={nonce}
     ↑ backend 校验 nonce 未过期 + 未被消费 → 标 consumed → 返回 short-lived token
     → { token, expires_at: now+10min, refreshHint }
  4. chrome.storage.local.set({ token, expires_at })
```

约束：

- **nonce 一次性**：`auth_link_nonces(nonce, user_id, consumed_at)`，consume 后任何 confirm 都 410。
- **manifest 锁源**：`externally_connectable.matches = ["https://findwith.com/*"]`，扩展只接受 https findwith.com 来源消息。
- **Origin 二次校验**：SW `chrome.runtime.onMessageExternal` handler 必须 `if (sender.origin !== 'https://findwith.com') return`。
- **content script 不参与**：网页 sendMessage 直达 SW，**不**经 content script 中转，避免 token / nonce 暴露给页面 DOM。
- **token 寿命短**：confirm 返回的 token 10min 过期，刷新走下面的标准路径。

**Token 刷新**：分两路径，因为 Clerk JS SDK 必须运行在有 DOM 的环境（其内部用跨域 iframe 拿 session cookie），SW 全局没有 `document`，无法直接调 `Clerk.session.getToken()`。

**Token 刷新**：分两路径，因为 Clerk JS SDK 必须运行在有 DOM 的环境（其内部用跨域 iframe 拿 session cookie），SW 全局没有 `document`，无法直接调 `Clerk.session.getToken()`。

```
请求时机     ───▶  Side Panel 是否打开？
                       │
            ┌──────────┴──────────┐
            ▼                     ▼
       已打开                  已关闭
       │                       │
       ▼                       ▼
  SW.fetch 返回 401         SW.fetch 返回 401
       │                       │
       │ port.postMessage      │ chrome.action.setBadgeText("!")
       │  REQ_REFRESH_TOKEN    │ + setBadgeBackgroundColor("#f59e0b")
       ▼                       │ + 把待发请求入 chrome.storage.local
  Side Panel React:            │   pending_requests[]（含 idempotency-key）
   await Clerk.session         │
        .getToken({skipCache}) │ 等用户点扩展图标 → Side Panel 打开
   → chrome.storage.local      │ → onMounted 读 pending_requests
        .set({token})          │ → 走"已打开"路径刷新 token
   → port.postMessage          │ → 重放 pending_requests
        TOKEN_REFRESHED        │
       ▼                       ▼
  SW retry 原请求          SW retry pending_requests
```

**关键约束（避免实现踩坑）**

- ⚠️ **不走 SW → Clerk REST 直刷**：SW 的 `fetch` 默认 `credentials: 'omit'`，即使设 `'include'` 也无法访问 `clerk.findwith.com` 域下的 third-party cookie（受 ITP/SameSite 限制）；Clerk 也不向前端暴露 refresh token。所以 Side Panel 关闭时**只能**等用户打开，无静默刷新方案。
- 队列上限：`pending_requests` 最多保留 50 条，超出丢弃最旧的并打 `auth.refresh.queue_overflow` telemetry。
- 用户长期不打开 Side Panel：badge 持续显示 "!"；用户发起任何 capture/apply 也会自动唤起 Side Panel（已在 8.2 BgMsg 加 `OPEN_SIDEPANEL`）。
- 提前刷新：SW 检测到 `expires_at - now < 5min` 时若 Side Panel 已开主动 `REQ_REFRESH_TOKEN`，避免在用户操作中途中断。

### 8.4 LinkedIn / Gmail content-script 防御

- 选择器分层：先 `aria-*` → 再 `data-*` → 最后 class fallback；任一层失败即上报 `cs.scrap.miss` telemetry
- DOM 抓取 sanitize：`DOMPurify` 白名单
- 不修改原页样式（除注入按钮）；按钮用 shadow root 隔离

**选择器配置远程化（Phase 1 Week 2 P1）**

LinkedIn/Gmail DOM 经常微调（一年 4-6 次类名变更），不能把选择器硬编码到扩展再走 Chrome Web Store 4-7 天审核。方案：

- SW 启动时 `fetch GET /v1/config/selectors?ext_version=<v>`（带 ETag），缓存到 `chrome.storage.local`
- Schema：`{"linkedin.job_detail.title": ["h1.t-24[data-test=...]", "section.jobs-...", "h1"], ...}`（每条按优先级尝试）
- content-script 注入时从 storage 读，不走打包
- 后端管理面：内部 `/admin/selectors` 增删改 → 立即推（content script 收到 `chrome.runtime.onMessage{type:'SELECTORS_UPDATED'}` 时热替换）
- 兜底：选择器全部 miss 时 fallback 到打包版本（保证扩展永远可用）

### 10.2 CI/CD（GitHub Actions）

```
on: push (branch: main, dev) / pull_request
jobs:
  proto:    buf lint + buf breaking + buf generate (artifact)
  backend:  ruff + mypy + pytest (with golden LLM replays via FakeProvider)
  extension:vitest + playwright (mock api) + zip artifact
  web:      typecheck + e2e (playwright)
  release:
    on: tag v*
    - upload extension zip → Chrome Web Store API (semi-auto)
    - render deploy hook → web/worker
    - alembic upgrade head（render build step）
```

**Proto 变更的部署顺序（强约束）**

protobuf 是三端唯一来源，schema 漂移会让客户端读到未声明字段直接崩。CI/CD 必须按以下偏序部署：

```
[buf push] → [backend deploy（含 alembic upgrade）] → [extension Chrome Web Store 发版] → [web Vercel deploy]
   ↑必须最先         ↑确保 endpoint 已能读写新字段        ↑用户更新到新版本（5-7 天审核）        ↑面向新老扩展同时兼容
```

具体规则：

- **加字段（向前兼容）**：backend 先发，extension/web 后发；老扩展继续工作（忽略未知字段）。
- **删字段或改语义（breaking）**：buf breaking 在 PR 必跑；要删字段必须等 Chrome Web Store 上**老版本 install 比例 < 5%**（看 `chrome.runtime.getManifest().version` 上报的 telemetry）；删除前先发"双读"backend，再发"删字段"backend。
- **enum 新增 value**：所有读端必须先升到能识别新 value 的版本（unknown enum 在 ext 端做兜底分支），再让 backend 写入新 value。
- **release gate**：tag v* 触发 release workflow 时，预检 `proto-version` ≥ `last-deployed-backend-proto-version`；倒序 tag 直接 fail。

实际拉链（举例：`Recommendation.click_signature` 加字段）：

1. PR-1：proto 加字段 + backend 写入 + 测试 → 合并 → backend deploy（老 ext 收到新字段忽略）
2. PR-2：extension 读字段 + 兜底（缺则 fallback 老逻辑）→ Chrome Web Store 上传 → 等审核
3. PR-3：审核过 + 用户安装率 > 95% → 后端可以开始依赖该字段做强校验

### 10.3 Migration 规约

- Alembic autogen 必须 review；
- **零停机迁移**：先发"加列+双写"PR，再发"切读"PR，再发"删旧"PR；不允许一个 PR 既改 schema 又改业务。

**Alembic 单一拥有者（共享 PG 强约束）**

产品端 backend 仓库（`backend/db/alembic/`）是**唯一**持有 alembic 目录的仓库；官网 Next.js 仓库不跑 `alembic upgrade`。原因：两个服务共享同一 Postgres，多源迁移会出现 revision 链分叉、表 owner 错乱、迁移并发死锁。

跨服务表归属：

| 表前缀 | 物理 schema 拥有者 | 业务写者 |
|---|---|---|
| `iam_*` | product backend alembic | 双方（webhook 创建 / 双方更新 settings） |
| `billing_*` | product backend alembic（**虽然由官网写**） | 官网 |
| `quota_*` / `outbox_*` / `idempotency_*` | product backend alembic | 双方各自范围 |

**流程**：官网需要新增 / 修改 billing 相关表 → 在 product backend 仓库提 alembic PR → 官网仓库 PR 在描述里引用对应 alembic revision → CI gate：官网部署前校验 `alembic current` ≥ 引用 revision。

**CI 强制**：官网仓库加一个 `db-schema-check` job，启动时 `pg_dump --schema-only` 与 `proto/expected_schema.sql` 对比，diff 非空则 fail。这保证官网代码不会先于 schema 上线。

### 10.5 备份 / 灾备（RTO / RPO）

v0.1 是单 region 部署（Render Oregon），不做 multi-AZ；DR 目标按"创业期可承受"定档，演进到 v0.2 再升级。

| 指标 | v0.1 目标 | 实现 | v0.2 演进 |
|---|---|---|---|
| **RPO**（最大数据丢失） | ≤ 24h | Render Postgres nightly logical dump（`pg_dump -Fc`）→ Cloudflare R2（跨区） | ≤ 5min（启用 PITR / WAL streaming） |
| **RTO**（最大恢复时间） | ≤ 4h | 从 R2 dump → 新 Render PG 实例 → DNS 切 → app rolling restart；操作手册 `docs/runbook/dr-restore.md` | ≤ 30min（hot standby + DNS health-check 自动 failover） |
| **R2 备份保留** | 7 daily + 4 weekly + 3 monthly（共 14 个 snapshot） | R2 lifecycle rule | 同 |
| **演练频率** | 每季度 1 次（staging restore + 数据完整性 hash 校验） | 计入 SRE on-call 周期 | 每月 |
| **关键不可重建数据** | 加密字段（resume bytes / email body / material.raw_text）；conversations；tailoring；recommendations | 同上 dump 覆盖；KEK 走 Doppler 独立备份（与 DB dump 解耦，恢复时分别注入） | 同 |

**对比加密备份**：DB dump 是密文（pgcrypto 字段已加密），KEK 不在 dump 里——这意味着即使 R2 备份泄漏，攻击者拿到的也是无 KEK 的密文。恢复时必须先在新进程注入 KEK 再 import dump，否则启动 fail-fast（见 §12.1）。

## 十二、安全 / 合规要点（与 v0.1 强约束的）

### 12.1 字段级加密与密钥管理

⚠️ **不写"密钥从 KMS 拉"——Render 没有原生 KMS 服务**。v0.1 接受的实务方案 + 风险标注：

| 项 | v0.1 实务 | 风险 / v0.2 演进 |
|---|---|---|
| 加密对象 | resume bytes、email body、material.raw_text | — |
| 加密方式 | `pgcrypto` field 级 AES-256（DEK） | — |
| DEK 存储 | **Render env var（accepted risk）** | 风险：管理员可见。v0.2 迁移到 Fly.io + AWS KMS 真正托管 |
| KEK 存储 | Doppler / 1Password Secrets Automation 启动时注入 process env | envelope encryption：env var 里的 DEK 是用 KEK 加密后的 ciphertext |
| 解密时机 | 进程启动从 KEK 解密 DEK 到内存，运行时不再持久化明文 DEK | — |
| 轮换 | DEK 90 天手工轮换（rewrap 全部密文）；KEK 半年 | v0.2 自动轮换 |

具体拉链：

```
启动序列:
  1. Doppler agent 注入 KEK 到 process env（Render Pre-Deploy hook 调用）
  2. App 读 env: DEK_CIPHERTEXT, KEK
  3. AES-decrypt(DEK_CIPHERTEXT, KEK) → DEK 明文常驻 memory
  4. unset env DEK_CIPHERTEXT (手动 del os.environ)
运行时:
  pgcrypto.encrypt(plaintext, DEK) → DB
```

**Day-1 强制启用 + fail-fast（不存在明文期）**

加密路径必须在 v0.1 launch 当天就位——**不允许先用明文跑几个月再回填**，原因是回填涉及全表 rewrite + 历史 telemetry / outbox 引用同一行，工作量与正确性远大于 day-1 落地。

启动 fail-fast 实现：

```python
# app/startup.py
def init_crypto():
    kek = os.environ.pop('KEK_B64', None)        # pop = 读后即删
    dek_ct = os.environ.pop('DEK_CIPHERTEXT_B64', None)
    if not kek or not dek_ct:
        sys.exit('FATAL: KEK / DEK_CIPHERTEXT not injected')
    try:
        dek = aes_decrypt(b64d(dek_ct), b64d(kek))
    except Exception as e:
        sys.exit(f'FATAL: DEK decrypt failed: {e}')
    # round-trip 自检
    probe = b'crypto-startup-probe'
    if aes_decrypt(aes_encrypt(probe, dek), dek) != probe:
        sys.exit('FATAL: crypto round-trip failed')
    app.state.dek = dek

# pgcrypto 字段也要在 startup 校验：随便 SELECT 一行加密列 + 解密成功
```

进程不能在缺密钥状态下接流量。Health probe（`/livez`）在 `app.state.dek` 缺失时返回 500，Render 会标 unhealthy 不接路由。

DB schema 强制：所有应加密字段类型为 `bytea`（不是 `text`），CHECK 约束 `length(col) > 16`（pgcrypto 输出至少有 IV + tag），插入明文 `text` 直接报类型错误。

## 十五、扩展 ↔ 官网同步协议（与 website-design 共享公约）

> 本章节是产品文档与官网文档的**公约**，两份文档同款落字。任何修改必须同步更新两侧。

### 15.1 设计目标

**问题**：用户在 findwith.com 完成订阅 / 取消 / 暂停 / 恢复后，浏览器扩展进程如何及时感知。

**核心原则**：
1. **后端 DB 是唯一真相源**。Stripe / Clerk 是写入侧，DB 是读取侧。
2. **客户端缓存仅供 UI 显示**。任何决策门禁（quota 扣减、特性开放）必须由后端在 endpoint 内重新读 DB 校验。
3. **多通道触发，单端点拉取**。多种事件触发"刷新"信号，但客户端始终从同一个 endpoint 拉权威值。

### 15.2 协议端点

#### 读侧 endpoints（产品端实现）

```
GET /v1/me/entitlements
  Headers: Authorization, If-None-Match
  Response 200:
    {
      "user_id": "...",
      "tier": "PRO",
      "effective_tier": "PRO",
      "state": "ACTIVE",
      "period_end": "2026-06-08T00:00:00Z",
      "feature_flags": {},
      "etag": "W/\"v1:...\"",
      "fetched_at": "..."
    }
  Response 304: 无 body（基于 If-None-Match）
  Cache-Control: private, max-age=60

GET /v1/me/quota
  Response 200:
    {
      "tailoring_completed": 1,
      "tailoring_limit": 3,         // FREE=3, PRO/PRO_PLUS=∞ (-1)
      "reco_today_consumed": 0,
      "reco_today_limit": 5,
      "as_of": "..."
    }
  Cache-Control: private, max-age=5
```

**为什么拆两个 endpoint**：tier 变化频率（小时-月级）远低于 quota 消费频率（每次 export）。合并会让 entitlements 缓存被 quota 写操作不必要地频繁失效。这是 GitHub API rate-limit、Stripe usage records 的成熟做法。

#### 写侧（官网实现，本文档不实现）

写侧端点 `POST /v1/billing/checkout/finalize` 与 `POST /v1/billing/webhooks/stripe` 由官网独立路由处理，实现细节见 `docs/tech/v0.1-website-design.md` §4.3。产品端只消费这两条路径**最终落库后的状态**——通过 ① externally_connectable / ② 60s 轮询 / ③ stale header 三个触发点拉取 `/v1/me/entitlements` 感知。

### 15.3 客户端三层同步机制

```
①  externally_connectable（即时通道）
    场景：用户刚在 findwith.com 付完，进入 /billing/success?session_id=cs_xxx
    success 页执行：
      a) await fetch('/v1/billing/checkout/finalize', {body:{session_id}})
      b) chrome.runtime.sendMessage(EXT_ID, {type:'ENTITLEMENTS_INVALIDATE'})
    扩展 SW 收到 → 立刻 fetch /v1/me/entitlements (cache:'no-store')
                 → 写 chrome.storage.local
                 → port 通知 Side Panel 重渲染
    manifest.externally_connectable.matches = ["https://findwith.com/*"]

②  60s TTL 兜底拉取
    触发点：SW 唤醒、Side Panel mount、API 收到 402 / 403、登录态变化
    实现：
      const cache = await chrome.storage.local.get('entitlements')
      if (cache && Date.now() - cache.fetched_at < 60_000) return cache
      else fetch with If-None-Match → 200 写盘 / 304 仅 touch fetched_at
    quota 用类似机制但 TTL=5s（消费快）

③  服务端强校验
    所有受限端点（/v1/tailoring/{id}/exports 等）：
      backend 内重新 SELECT entitlements + quota，不信任客户端缓存
      不满足 → 402 Payment Required + Error{code:'FW.QUOTA.EXCEEDED'} + upgrade_prompt
    扩展端 ② 与 ③ 之间最长滞后 60s，但 ③ 永远正确
```

**反模式（不做）**：

- ❌ JWT 内嵌 tier 作真相源 —— Clerk JWT TTL 60s 引入分钟级延迟，不如直接拉 endpoint
- ❌ SSE 长连推送 EntitlementsChanged —— MV3 SW 上 SSE 是按 turn 开的，且每用户长连成本高，收益重叠 ②
- ❌ Stripe webhook 直接通知扩展 —— 扩展不可能注册公网 endpoint，必须经过后端

### 15.4 边界场景

| 场景 | 同步路径 | 滞后 |
|---|---|---|
| 用户在 findwith.com 付完订阅 | ①（finalize 同步落库 + 触发扩展） | <1s |
| 用户在 Stripe Customer Portal 取消 | ②（webhook → DB；扩展下次 ② 拉到） | ≤60s |
| 跨设备：手机付费、桌面用扩展 | ②（桌面扩展 60s 内 ② 触发） | ≤60s |
| 卡欠费 PAST_DUE | ②（webhook 写 DB；扩展下次拉到） | ≤60s |
| 用户接 offer 触发 farewell → 订阅暂停 | 产品端发 OfferAccepted 事件 → 官网订阅 → Stripe pause → DB 更新 → ② 拉到 | ≤60s + 官网处理时间 |
| 用户清空浏览器数据 | 下次启动 SW → ② 拉到 | 启动时 |

### 15.5 防伪 / 防绕过

- 客户端 entitlements 仅做 UI（banner 显示、徽章）。不做决策门禁。
- 所有 entitlement-gated endpoint 服务端二次校验（量化数据从 DB 读，不信 header / body）。
- externally_connectable 消息只信 origin，不信 payload；payload 仅作"触发器"，刷新动作走标准 endpoint。
- /v1/me/entitlements 必带 Clerk JWT；用户改 storage 把 tier 改成 PRO_PLUS 在受限端点会被 ③ 拒绝。

### 15.6 失败模式与降级

| 失败 | 降级行为 |
|---|---|
| externally_connectable 消息丢失（用户 disable 扩展之类） | ② 60s 兜底覆盖 |
| /v1/me/entitlements 5xx | 沿用 stale cache + telemetry `entitlements.refresh.fail`；UI 不变 |
| finalize 失败但 webhook 成功 | ② 拉到 webhook 写入的状态；UI 滞后 60s |
| finalize 成功但 webhook 失败 | finalize 已落 DB，webhook 重试或人工补 |
| 用户清空浏览器数据 | cache 全失，下次 SW 启动从 ② 轮询恢复；中间用户操作受限端点会被 ③ stale header 强制刷新 |
| 扩展长期不开（数月） | alarm 不触发，下次开 Side Panel 时 ③ stale header 强制刷新；必要时引导重新登录 |

### 15.8 跨服务 outbox 消费契约

`outbox_events` 是产品端 + 官网两侧共享的发布表，多个 consumer 各自按需订阅。为避免重复消费 / 漏消费 / 服务交叉时事件归属不清，订阅契约硬约定：

**Consumer Group 命名**：`<service>:<purpose>`，例：

| consumer_group | 拥有者 | 订阅 event_type | 用途 |
|---|---|---|---|
| `billing:offer-pause` | 官网订阅 service | `OfferAccepted` | 调 stripe.subscriptions.update pause |
| `product:entitlements-cache-bust` | 产品 backend | `EntitlementsChanged` | 失效 in-process 缓存、推 SSE 给在线扩展 |
| `product:reco-trigger` | 产品 worker | `DailyRecoCronFired` | 启动 build_daily_reco |
| `audit:all-events` | 后续审计 service（v0.2） | `*` | 全量归档到 S3 |

**消费状态**：

```sql
CREATE TABLE outbox_subscriptions (
  consumer_group text PRIMARY KEY,
  last_event_id  ULID NOT NULL,        -- 单调推进游标
  updated_at     timestamptz NOT NULL
);
CREATE TABLE outbox_processed (
  consumer_group text NOT NULL,
  event_id       ULID NOT NULL,
  processed_at   timestamptz NOT NULL,
  PRIMARY KEY (consumer_group, event_id)
);
```

**至少一次 + 幂等**：consumer 处理 event 前先 `INSERT ... ON CONFLICT DO NOTHING` 到 `outbox_processed`；若 conflict（事件已处理）直接 ack，跳过 handler；推进 `last_event_id`。这保证：crash 重启后 replay 的事件不会触发副作用二次执行。

**通知 + 兜底拉**：

- 实时：发布者 `pg_notify('outbox_changed', event_type)`；consumer LISTEN 到通知后 `SELECT * FROM outbox_events WHERE id > :last_event_id LIMIT 100`。
- 兜底：consumer 每 5s 主动 poll（防 LISTEN 链路断、防进程刚启动来不及订阅）。

**事件 schema 校验**：所有 event payload 必须是 protobuf 序列化的 `OutboxEvent`（`event_type` enum + bytes payload）。consumer 反序列化失败 → DLQ → Sentry alert。protobuf schema 走 §三 + §10.2 部署偏序，不允许"先发布新 event 类型 后发 consumer 升级"。

**保留 / 清理**：`outbox_events` 保留 30 天（`processed=true AND created_at < now-30d` 由后台 job 删）；`outbox_processed` 跟 events 同步清理。
