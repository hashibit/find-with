### 1.2 关键架构决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 官网 stack | **Next.js 14 App Router + Vercel** | SEO + RSC 性能 + 与扩展（React）共享组件库的可能 |
| 后端 API | **复用产品后端 FastAPI（共享 PG + Clerk）** | 不另起服务；通过路由前缀 `/v1/billing/*` 与扩展路由隔离 |
| Auth | **Clerk（hosted UI + JWT）** | 同 Clerk 实例服务于扩展和官网，JWT 可在两端复用 |
| 计费 | **Stripe（Checkout + Customer Portal）** | 不自建计费 UI，Stripe Hosted 解决 PCI / VAT / 退款流 |
| 扩展通知 | **externally_connectable + 共享 DB** | 详见 §9 协议 |

### 1.3 不做（v0.1）

- 不自建定价后台/优惠券系统（用 Stripe Coupon）
- 不做 referral / affiliate（v0.2）
- 不做客服在线聊天（用邮件 support@findwith.com）
- 不做多语言（仅 en-US）
- 不做 self-serve team plan（v0.3）

### 2.1 关键 UX 流

#### 新用户注册到首次使用

```
用户 → / (Landing) → 点 "Install Extension"
     → /install → Chrome Web Store
     → 装完扩展 → 扩展 Side Panel 弹欢迎 → 点 "Sign in or create account"
     → SW chrome.tabs.create('https://findwith.com/login?return=ext')
     → /login Clerk → 完成 → /auth/extension-callback
        → chrome.runtime.sendMessage(EXT_ID, {type:'AUTH_TOKEN_SET', token})
        → window.close()
     → 扩展自动进入 onboarding
```

#### 升级到 Pro

```
[扩展端触发] 用户在扩展点 upgrade banner / 用完 free quota 看到弹窗
  → SW chrome.tabs.create('https://findwith.com/billing/upgrade?plan=pro')
[官网] /billing/upgrade
  → 检查登录态（Clerk）；未登录 → /login?return=billing/upgrade
  → 已登录 → POST /v1/billing/checkout {plan:'pro'} → 拿 hosted_url
  → window.location = hosted_url
[Stripe Checkout 页面] 用户填卡 → 支付成功
  → Stripe redirect → /billing/success?session_id=cs_xxx
[官网] /billing/success
  → POST /v1/billing/checkout/finalize {session_id} → 后端落 DB → 200 {tier:PRO}
  → chrome.runtime.sendMessage(EXT_ID, {type:'ENTITLEMENTS_INVALIDATE'})
  → UI 显示 "Welcome to Pro 🎉"，2s 后跳 /dashboard
[扩展] SW 收到消息 → fetch /v1/me/entitlements → 缓存更新 → port 推 Side Panel
       → Side Panel 实时切到 Pro UI（隐藏 banner、显示徽章）
```

#### 接 offer 后订阅暂停 + 后续恢复

```
[扩展] 用户在雷达标 OFFER_ACCEPTED → DomainEvent: OfferAccepted（写 outbox）
[官网订阅 service] 订阅此事件（pg_notify / outbox publisher）
  → POST 内部：BillingService.pause(user_id, reason='OFFER_ACCEPTED')
  → stripe.subscriptions.update(sub_id, pause_collection={behavior:'mark_uncollectible'})
  → 写 billing_subscriptions(state=PAUSED, paused_reason='OFFER_ACCEPTED', period_end 保持)
  → outbox: EntitlementsChanged
[扩展] 60s 内 ② 拉到 entitlements (state=PAUSED) → farewell 流继续

[数月后] 用户重新打开扩展
  → SW 启动 ② 拉 entitlements → state=PAUSED
  → Side Panel 顶部 banner: "Welcome back. Resume Pro to continue."
[用户点 banner]
  → SW chrome.tabs.create('https://findwith.com/billing/resume')
[官网] /billing/resume
  → 显示确认页 "Resume now. Charged today, next $X on yyyy-mm-dd."
  → 用户确认 → POST /v1/billing/resume
  → backend: stripe.subscriptions.update(sub_id, pause_collection='')
              billing_subscriptions(state=ACTIVE, period_end=今日+30d)
              outbox: EntitlementsChanged
  → chrome.runtime.sendMessage(EXT_ID, ENTITLEMENTS_INVALIDATE)
  → 跳 /dashboard "Welcome back to Pro"
[扩展] 同步刷新到 ACTIVE/PRO；agent 推 "好，继续。从这次 offer 复盘开始？"
```

#### 账号注销

```
[官网] /dashboard/account → 点 "Delete account" → 二次确认 + 输入 email 验证
  → POST /v1/iam/account:delete
[backend AccountPurgeSaga（详见 §7）]
  step 1: 写 iam_users.deleted_at = now (soft) + 24h 撤销窗口
  step 2: 立即停 Stripe billing（防继续扣费），但保留 customer 24h 撤销窗口
  step 3: 邮件用户 "已计划注销，24h 内可撤销"
[24h 后 cron] saga 推进
  step 4: 删 S3 对象（resume / pdf / snapshot）
  step 5: stripe.customers.delete(stripe_customer_id)
  step 6: clerk.users.deleteUser(clerk_user_id)   ← 不可逆，最后做
  step 7: hard delete 所有产品域数据（profile/jobs/...）
  failure: 任意步骤失败 5 次重试 → dead_letter + Sentry alert
```

### 4.3 Finalize（防 redirect-vs-webhook 竞态）

```python
@router.post('/v1/billing/checkout/finalize')
async def finalize(req: FinalizeCheckoutRequest, user=Depends(current_user)):
    session = stripe.checkout.sessions.retrieve(req.session_id, expand=['subscription'])
    if session.metadata.user_id != user.id:
        raise HTTPException(403)
    if session.payment_status != 'paid':
        raise HTTPException(409, 'Payment not completed')

    sub = session.subscription
    # idempotent UPSERT
    async with db.transaction():
        existing = await db.fetch_one(
            "SELECT * FROM billing_subscriptions WHERE user_id=:uid FOR UPDATE",
            {'uid': user.id})
        target = build_subscription_from_stripe(sub, user)
        if not existing or existing.updated_at < target.updated_at:
            await db.execute(upsert_subscription, target.model_dump())
            await write_outbox('EntitlementsChanged', {'user_id': user.id})
    return target
```

webhook 收到同一 sub 的事件时，若 finalize 已写入更新版本则 noop。

### 4.4 Stripe Webhook 处理

订阅相关事件：

| Stripe Event | 处理 |
|---|---|
| `checkout.session.completed` | 同 finalize 落库（兜底）|
| `customer.subscription.created` | 创建 subscription 行 |
| `customer.subscription.updated` | 更新 tier / state / period_end |
| `customer.subscription.deleted` | state=CANCELED |
| `customer.subscription.paused` | state=PAUSED |
| `customer.subscription.resumed` | state=ACTIVE |
| `invoice.payment_failed` | state=PAST_DUE |
| `invoice.payment_succeeded` | state 根据 sub 状态校正 |

每条事件用 `idempotency_keys` 表去重（key=`stripe_event:evt_xxx`，TTL 30d）。

```python
@router.post('/v1/billing/webhooks/stripe')
async def stripe_webhook(request: Request):
    sig = request.headers.get('stripe-signature')
    body = await request.body()
    try:
        event = stripe.Webhook.construct_event(body, sig, STRIPE_WEBHOOK_SECRET)
    except SignatureVerificationError:
        raise HTTPException(400)

    if await idempotency_seen(f'stripe_event:{event.id}'):
        return {'deduped': True}

    handler = STRIPE_EVENT_HANDLERS.get(event.type)
    if not handler:
        return {'processed': False, 'reason': 'unhandled_event_type'}

    await handler(event.data.object)
    await idempotency_mark(f'stripe_event:{event.id}', ttl=30*86400)
    await write_outbox('EntitlementsChanged', {'user_id': resolve_user_id(event)})
    return {'processed': True}
```

### 4.6 暂停 / 恢复（farewell）

**暂停**由产品端事件触发（用户标 OFFER_ACCEPTED）：

```
[官网订阅 service] 订阅 outbox: OfferAccepted
  → BillingService.pause_subscription(user_id, reason='OFFER_ACCEPTED')
  → stripe.subscriptions.update(sub_id, pause_collection={behavior:'mark_uncollectible'})
  → DB: state=PAUSED, paused_reason='OFFER_ACCEPTED'
  → outbox EntitlementsChanged
```

**恢复**由用户主动从 banner 触发：详见 §2.1 流程。Stripe 调用：

```python
stripe.subscriptions.update(sub_id, pause_collection='')
# Stripe 会从今日起计算新一期，不补收暂停期间费用
```

DB 写：`state=ACTIVE, period_end=now + 30d, paused_reason=null`。

### 5.1 billing_subscriptions

```sql
CREATE TABLE billing_subscriptions (
  user_id text PRIMARY KEY REFERENCES iam_users(id),
  tier text NOT NULL CHECK (tier IN ('FREE','PRO','PRO_PLUS')),
  state text NOT NULL CHECK (state IN ('ACTIVE','PAUSED','CANCELED','PAST_DUE','GRACE')),
  stripe_customer_id text,
  stripe_subscription_id text UNIQUE,
  current_period_end timestamptz,
  paused_reason text,
  paused_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  -- 写入时打 advisory lock，防 finalize/webhook 并发覆盖
  CHECK ( (state='PAUSED') = (paused_at IS NOT NULL) )
);
CREATE INDEX ON billing_subscriptions (state, current_period_end);
```

## 七、三方一致性 Saga（账号注销）

详见产品文档 §14.5（saga 模式说明）。本文档列出官网的 step 编排（账号注销特有）：

```python
class AccountPurgeSaga:
    STEPS = [
        Step('soft_delete_local',         compensate='restore_local',         timeout='5s'),
        Step('pause_stripe_billing',      compensate='resume_stripe_billing', timeout='10s'),
        Step('email_user_confirmation',   compensate=None,                    timeout='30s'),
        # ↑ 上面三步在用户点 delete 后立即执行
        # ↓ 24h 后定时唤醒 saga 推进剩余
        Step('wait_24h_grace',            compensate=None,                    timeout='86400s'),
        Step('purge_s3_objects',          compensate=None,                    timeout='5m'),
        Step('delete_stripe_customer',    compensate=None,                    timeout='30s'),
        Step('hard_delete_local_data',    compensate=None,                    timeout='5m'),
        Step('delete_clerk_user',         compensate=None,                    timeout='30s'),
        # ↑ 不可逆，最后做
    ]
```

24h 撤销机制：用户在 grace 期内点 "Cancel Deletion" → saga `status=canceled`，回滚步骤 1-2（restore_local + resume_stripe_billing）。

failures：任一步重试 5 次（指数退避 10s/30s/2m/10m/1h）后入 `dead_letter`，触发 Sentry fatal alert + 邮件 ops。

## 九、扩展 ↔ 官网同步协议（与产品文档 §15 同款）

> 本章节是产品文档与官网文档的**公约**，两份文档同款落字。任何修改必须同步更新两侧。

### 9.1 设计目标

**问题**：用户在 findwith.com 完成订阅 / 取消 / 暂停 / 恢复后，浏览器扩展进程如何及时感知。

**核心原则**：
1. **后端 DB 是唯一真相源**。Stripe / Clerk 是写入侧，DB 是读取侧。
2. **客户端缓存仅供 UI 显示**。任何决策门禁（quota 扣减、特性开放）必须由后端在 endpoint 内重新读 DB 校验。
3. **多通道触发，单端点拉取**。多种事件触发"刷新"信号，但客户端始终从同一个 endpoint 拉权威值。

### 9.2 协议端点

#### 读侧 endpoints（产品端实现）

```
GET /v1/me/entitlements
  Headers: Authorization, If-None-Match
  Response 200:
    {
      "user_id": "...",
      "tier": "PRO",
      "effective_tier": "PRO",
      "state": "ACTIVE",
      "period_end": "2026-06-08T00:00:00Z",
      "feature_flags": {},
      "etag": "W/\"v1:...\"",
      "fetched_at": "..."
    }
  Response 304: 无 body（基于 If-None-Match）
  Cache-Control: private, max-age=60

GET /v1/me/quota
  Response 200:
    {
      "tailoring_completed": 1,
      "tailoring_limit": 3,
      "reco_today_consumed": 0,
      "reco_today_limit": 5,
      "as_of": "..."
    }
  Cache-Control: private, max-age=5
```

**为什么拆两个 endpoint**：tier 变化频率（小时-月级）远低于 quota 消费频率（每次 export）。合并会让 entitlements 缓存被 quota 写操作不必要地频繁失效。

#### 写侧（官网实现）

`POST /v1/billing/checkout/finalize` —— Stripe Checkout 成功后由 success 页同步调用，**不等 webhook**：

```
POST /v1/billing/checkout/finalize
  Body: { session_id: "cs_xxx" }
[backend website service]
  1. stripe.checkout.sessions.retrieve(session_id, expand=['subscription'])
  2. 落 billing_subscriptions（idempotent，与 webhook 同 sub_id 时合并）
  3. 写 outbox: EntitlementsChanged
  Response: { tier, effective_tier, state, period_end }
```

`POST /v1/billing/webhooks/stripe` —— Stripe 异步 webhook 兜底（防 finalize 失败）。

### 9.3 客户端三层同步机制

```
①  externally_connectable（即时通道）
    场景：用户刚在 findwith.com 付完，进入 /billing/success?session_id=cs_xxx
    success 页执行：
      a) await fetch('/v1/billing/checkout/finalize', {body:{session_id}})
      b) chrome.runtime.sendMessage(EXT_ID, {type:'ENTITLEMENTS_INVALIDATE'})
    扩展 SW 收到 → 立刻 fetch /v1/me/entitlements (cache:'no-store')
                 → 写 chrome.storage.local
                 → port 通知 Side Panel 重渲染
    manifest.externally_connectable.matches = ["https://findwith.com/*"]

②  60s TTL 兜底拉取
    触发点：SW 唤醒、Side Panel mount、API 收到 402 / 403、登录态变化
    实现：
      const cache = await chrome.storage.local.get('entitlements')
      if (cache && Date.now() - cache.fetched_at < 60_000) return cache
      else fetch with If-None-Match → 200 写盘 / 304 仅 touch fetched_at
    quota 用类似机制但 TTL=5s（消费快）

③  服务端强校验
    所有受限端点（/v1/tailoring/{id}/exports 等）：
      backend 内重新 SELECT entitlements + quota，不信任客户端缓存
      不满足 → 402 Payment Required + Error{code:'FW.QUOTA.EXCEEDED'} + upgrade_prompt
    扩展端 ② 与 ③ 之间最长滞后 60s，但 ③ 永远正确
```

**反模式（不做）**：

- ❌ JWT 内嵌 tier 作真相源 —— Clerk JWT TTL 60s 引入分钟级延迟，不如直接拉 endpoint
- ❌ SSE 长连推送 EntitlementsChanged —— MV3 SW 上 SSE 是按 turn 开的，且每用户长连成本高，收益重叠 ②
- ❌ Stripe webhook 直接通知扩展 —— 扩展不可能注册公网 endpoint，必须经过后端

### 9.4 边界场景

| 场景 | 同步路径 | 滞后 |
|---|---|---|
| 用户在 findwith.com 付完订阅 | ①（finalize 同步落库 + 触发扩展） | <1s |
| 用户在 Stripe Customer Portal 取消 | ②（webhook → DB；扩展下次 ② 拉到） | ≤60s |
| 跨设备：手机付费、桌面用扩展 | ②（桌面扩展 60s 内 ② 触发） | ≤60s |
| 卡欠费 PAST_DUE | ②（webhook 写 DB；扩展下次拉到） | ≤60s |
| 用户接 offer 触发 farewell → 订阅暂停 | 产品端发 OfferAccepted 事件 → 官网订阅 → Stripe pause → DB 更新 → ② 拉到 | ≤60s + 官网处理时间 |

### 9.5 防伪 / 防绕过

- 客户端 entitlements 仅做 UI（banner 显示、徽章）。不做决策门禁。
- 所有 entitlement-gated endpoint 服务端二次校验（量化数据从 DB 读，不信 header / body）。
- externally_connectable 消息只信 origin，不信 payload；payload 仅作"触发器"，刷新动作走标准 endpoint。
- /v1/me/entitlements 必带 Clerk JWT；用户改 storage 把 tier 改成 PRO_PLUS 在受限端点会被 ③ 拒绝。

### 9.6 失败模式与降级

| 失败 | 降级行为 |
|---|---|
| externally_connectable 消息丢失 | ② 60s 兜底覆盖 |
| /v1/me/entitlements 5xx | 沿用 stale cache + telemetry；UI 不变 |
| finalize 失败但 webhook 成功 | ② 拉到 webhook 写入的状态；UI 滞后 60s |
| finalize 成功但 webhook 失败 | finalize 已落 DB，webhook 重试或人工补 |
| 用户清空浏览器数据 | cache 全失，下次 SW 启动从 ② 轮询恢复；中间用户操作受限端点会被 ③ stale header 强制刷新 |
| 扩展长期不开（数月） | alarm 不触发，下次开 Side Panel 时 ③ stale header 强制刷新；必要时引导重新登录 |

### 9.7 telemetry

```
entitlements.refresh.{trigger=external_msg|panel_mount|sw_wake|api_402|cache_expire}
entitlements.tier_changed (props={from, to})
entitlements.staleness (cache_age_ms at use)
quota.refresh.{trigger}
quota.exceeded (props={feature, tier, limit})
billing.finalize.{success,fail}      # 由官网打
billing.webhook.{verify_fail, processed, dedup_hit}   # 由官网打
```
